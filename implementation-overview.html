Telegram MVP Approvals Proactivity

What the implementation is doing

This implementation adds a gateway-side control plane around the existing agent. The agent still focuses on model + tool execution, while Telegram, approvals, and reminders are handled outside it.

1. Telegram message flow

Telegram long-polling receives a private chat message.
The gateway checks the sender against gateway.telegram.allowedUserIds.
The chat/user pair is mapped to a persistent session via conversation bindings.
Commands like /new, /session, /remind, /approvals, /approve, and /deny are handled directly in the gateway.
Normal text is sent into the agent for a turn in the bound session.
The reply is chunked into Telegram-safe message sizes and sent back.

2. Dangerous-action policy

Before a tool runs, the gateway policy classifies it as allow, ask, or deny.

  • Allow: read-only tools like read, grep, glob, websearch, webfetch
  • Ask: write, edit, and mutating bash
  • Deny: obviously destructive or exfiltration-like bash commands

For bash, a risk classifier distinguishes safe read-only commands from mutating or high-risk ones.

3. Approval workflow

If a Telegram-requested tool needs approval, the gateway creates a persisted pending approval record.
The current turn stops with an approval-required response instead of running the tool.
The user can inspect pending items with /approvals.
The user resolves one with /approve <id> or /deny <id>.
A new follow-up turn is injected into the same session saying the action was approved or denied.

This avoids full paused-turn resumption while still letting the agent continue from the approval outcome.

4. Reminders and proactivity

The gateway supports opt-in one-shot reminders created via /remind.

  • Tasks are persisted in a scheduled-task store.
  • A scheduler periodically scans for due tasks.
  • Due tasks are claimed, executed, and only marked complete after success.
  • If execution fails, the claim is released so the reminder can retry later.

5. Fail-fast behavior

  • Explicit session lookups now fail instead of silently creating a new session.
  • Pending approvals cannot be resolved by the wrong Telegram actor.
  • Telegram polling uses abortable fetch so shutdown can stop an in-flight long poll promptly.
  • JSON decoding is allowed to fail loudly instead of silently masking invalid state.

6. Main code areas

  • src/gateway/telegram/* — Telegram transport, commands, polling, formatting
  • src/gateway/approvals/service.ts — approval orchestration
  • src/gateway/proactivity/* — scheduler and reminder execution
  • src/lib/conversation-bindings.ts — Telegram chat → session mapping
  • src/lib/policy/* — risk and tool policy logic
  • src/lib/proactivity/* — scheduled task persistence
